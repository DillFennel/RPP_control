# Как читать код из презентаций и этой заготовки

Сначала открыть `server/server.cpp` и найти `main`. Порядок сетевых действий совпадает с примером TCP-сервера из презентации. Затем прочитать `client/client.cpp`.

## Сервер

1. `socket(AF_INET, SOCK_STREAM, 0)` создаёт TCP-сокет для IPv4.
2. Поля `sockaddr_in` описывают локальный адрес: INADDR_ANY и порт 12345.
3. `bind` применяет этот адрес к сокету через ОС.
4. `listen` разрешает принимать подключения.
5. `accept` возвращает отдельный сокет подключившегося клиента.
6. Внутренний цикл читает команды, выполняет их и отправляет ответы.
7. После отключения или QUIT клиентский сокет закрывается, сервер снова вызывает accept.

Слушающий сокет и клиентский сокет — разные дескрипторы. Новые подключения ожидают обработки, пока сервер занимается текущим клиентом.

## Клиент

1. Создаёт свой сокет.
2. Заполняет адрес сервера. По умолчанию это 127.0.0.1:12345.
3. Вызывает connect. Локальный адрес и свободный порт назначает ОС.
4. Читает строку из консоли, отправляет её и получает ответ.
5. Разбирает OK VALUE, OK BYE или ERR.
6. После QUIT явно закрывает свой сокет.

Заполнение структуры адреса само по себе не меняет сокет: сервер использует структуру в bind, клиент — в connect. `htons` переводит порт в сетевой порядок байтов, `inet_pton` преобразует текст IP-адреса.

## Зачем receiveLine

В TCP один send не обязан соответствовать одному recv. Например, команда SET 10 может прийти несколькими частями, а две команды — одним большим блоком.

В этой заготовке recv просит **один байт** за вызов:

```cpp
char c;
recv(sock, &c, 1, 0);
```

Функция добавляет байты в строку, пока не встретит LF. Если сразу пришли две команды, байты второй остаются в приёмном буфере ОС до следующего вызова receiveLine. Если пришла часть команды, recv ждёт продолжения.

Это медленнее чтения большими блоками, зато для коротких команд намного проще объяснить framing. Ограничение 1024 байта не позволяет бесконечно накапливать слишком длинную строку.

`ReadResult` — обычное перечисление, дающее понятные имена результатам:

| Результат | Значение |
| --- | --- |
| LINE_OK | Полная строка получена |
| CLOSED | Другая сторона закончила передачу, неполной строки нет |
| IO_ERROR | Сетевая ошибка |
| TOO_LONG | Превышена длина строки |
| INCOMPLETE | Передача закончилась посередине строки |

## Зачем sendLine

Функция добавляет LF к строке и вызывает send. Если send принял только часть байтов, переменная sent увеличивается на это количество, и функция отправляет остаток.

Получение строки и её отправка нужны обеим программам, поэтому эти две короткие функции повторены в двух исходниках. Скрытых зависимостей на другие файлы нет.

## Где менять задачу

В сервере есть функция `handleCommand`. Она получает строку запроса, ссылку на value и ссылку на quit.

- `value` хранит состояние текущего соединения.
- `quit` становится true после корректной команды QUIT.
- Возвращаемая строка — ответ клиенту, без LF.

Аргументы разбираются через `std::istringstream`: строка читается как поток ввода. Проверка лишнего токена запрещает SET 1 2. Дополнительная проверка после числа запрещает 12abc. Слишком большое число тоже вызывает ошибку чтения.

Для ADD переполнение проверяется **до сложения** через LLONG_MIN и LLONG_MAX. При ошибке value не изменяется.

Чтобы добавить NEGATE, добавить ветку в handleCommand и обновить протокол. Для LLONG_MIN смена знака невозможна: положительный результат не помещается в long long. Ответ OK VALUE уже умеет разбирать клиент.

## Windows и macOS

| Windows | macOS |
| --- | --- |
| SOCKET | int |
| INVALID_SOCKET при ошибке socket/accept | -1 |
| WSAStartup перед сетевыми вызовами | Отдельная инициализация не нужна |
| closesocket | close |
| WSACleanup в конце | Не требуется |
| shutdown(..., SD_SEND) | shutdown(..., SHUT_WR) |
| Библиотека ws2_32 | Сокеты доступны из системной библиотеки |

На macOS SIGPIPE игнорируется одной строкой, чтобы отправка в закрытое соединение возвращала ошибку send вместо завершения процесса. Свой обработчик Ctrl+C не используется.
