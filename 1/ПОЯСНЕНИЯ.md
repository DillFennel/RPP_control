# Как работает код

Читать вместе с исходниками выбранной платформы: [Windows](windows/) или [macOS](macos/).

## Общая схема

Клиент читает строку из консоли, добавляет LF, отправляет её серверу и ждёт ответ. Сервер выделяет полную строку из TCP-потока, проверяет команду и аргументы, выполняет действие и отправляет одну строку ответа.

```text
Клиент                              Сервер
socket                              socket
                                    bind
                                    listen
connect --------------------------> accept
send_all("SET 10\n") -------------> read_line
                                    handle_command
read_line <------------------------ send_all("OK VALUE 10\n")
```

У клиента и сервера разные сокеты. В TCP-сервере дополнительно есть слушающий сокет и отдельный сокет принятого соединения. Дескриптор сокета — локальное обозначение ресурса внутри процесса; по сети этот номер не передаётся.

## Адреса и подключение

`sockaddr_in` — обычная структура с IPv4-адресом и портом. Заполнение её полей само по себе не меняет сокет.

`bind(listener, ...)` сообщает ОС, какой локальный адрес и порт закрепить за слушающим сокетом. В примере используется порт 12345 и INADDR_ANY — все локальные IPv4-интерфейсы.

`connect(connection, ...)` получает удалённый адрес сервера. Если клиент не сделал bind, ОС автоматически выбирает его локальный адрес и свободный порт. Например:

```text
клиент 127.0.0.1:53127 <------ TCP ------> сервер 127.0.0.1:12345
```

`listen` разрешает принимать подключения. `accept` возвращает сокет конкретного соединения. У него сохраняется локальный серверный порт 12345; TCP различает соединения по адресам и портам обеих сторон.

`htons` переводит 16-битный номер порта в сетевой порядок байтов. `htonl` делает соответствующее преобразование для 32-битного числа. `inet_pton` превращает текст IPv4-адреса в двоичное представление.

## Почему одного send и одного recv недостаточно

TCP передаёт поток байтов. Границы вызовов send не сохраняются.

Если клиент отправил `GET\nADD 5\n`, сервер может получить:

```text
recv №1: "GE"
recv №2: "T\nADD 5\n"
```

Возможен и один recv со всей строкой, и много меньших чтений. Поэтому `read_line` добавляет полученные байты в `pending`, а `extract_line` извлекает одну строку по LF. Остаток сохраняется для следующего запроса.

`recv` возвращает число полученных байтов и не дописывает нулевой байт. Поэтому используется `pending.append(buffer, n)`, а не strlen(buffer). Возврат 0 в TCP означает штатное завершение отправки другой стороной. Если перед этим остался неполный запрос без LF, сервер возвращает INCOMPLETE_MESSAGE, когда соединение ещё позволяет отправить ответ.

`send` тоже может принять только часть данных. Функция `send_all` увеличивает позицию на фактически отправленное число байтов и повторяет вызов для оставшейся части.

Успешный send означает, что данные приняла локальная сетевая подсистема. TCP ACK подтверждает приём данных TCP другой стороны. Выполнение команды подтверждается прикладным ответом `OK VALUE ...` или `OK BYE`.

## Где находится логика варианта

Файл `server/commands.hpp` содержит структуру `Session` и функцию `handle_command`.

`Session` создаётся внутри `serve_client`, поэтому каждое соединение получает собственное значение 0. При выходе из функции состояние уничтожается.

`handle_command` проверяет запрос в следующем порядке:

1. Допустимые байты текста.
2. Наличие и имя команды.
3. Количество аргументов.
4. Формат и диапазон числа.
5. Возможность выполнения операции.
6. Изменение состояния и формирование ответа.

Границы сообщения проверяются раньше, в сетевом слое. При ошибке команды состояние не меняется.

`from_chars` преобразует аргумент в int64 без исключений. Дополнительно проверяется, что разобран весь аргумент: `12abc` отклоняется. Проверка переполнения ADD выполняется до сложения, поскольку переполнение знакового целого недопустимо.

Клиент использует `parse_reply` из `common/protocol.hpp`: отличает VALUE, BYE, ERR и некорректный ответ. Для новых форматов ответов обновить этот разбор и вывод в `client/main.cpp`.

## Закрытие сокетов и остановка

Класс `Socket` владеет одним дескриптором. Его деструктор вызывает closesocket в Windows или close в macOS. Копирование запрещено, чтобы два объекта не пытались закрыть один ресурс.

В Windows класс `Winsock` вызывает WSAStartup при создании и WSACleanup при уничтожении. Он создаётся раньше сокетов, поэтому уничтожается после них.

На macOS специальная инициализация сети не нужна. Опция SO_NOSIGPIPE защищает процесс от завершения сигналом при отправке в закрытое соединение: программа получает обычную ошибку send.

После QUIT сервер отправляет OK BYE и завершает отправку через shutdown. Затем RAII освобождает сокет. Ctrl+C сервера устанавливает флаг остановки; основной код замечает его и выходит из цикла. select ожидает готовности с короткими паузами, чтобы регулярно проверять флаг.

## Ограничения учебной заготовки

Сервер обслуживает одного клиента за раз. Второй клиент может уже установить TCP-соединение, но его команды будут обработаны после завершения первой сессии.

Входящие сообщения используют ASCII. При добавлении текстовых полей на русском языке нужно определить кодировку и обновить валидацию, а также протокол.

Таймаута бездействия на приём нет: короткий запрос без LF ждёт продолжения. Таймаут одной блокирующей операции send — 5 секунд.
