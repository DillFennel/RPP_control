# Пояснения к варианту 5

Начинай чтение с `main` в SERVER/server.cpp, затем открой CLIENT/client.cpp. Обе версии выполняют одинаковые команды; различается только системный API сокетов.

## Как проходит запрос

```text
Клиент: ввод /generate DIGITS 4
  → sendLine добавляет LF и отправляет строку
Сервер: receiveLine читает до LF
  → handleCommand выбирает алфавит 0123456789
  → генератор четыре раза выбирает индекс символа
  → результат добавляется в историю
  → sendLine отправляет OK STRING <результат>
Клиент: receiveLine получает ответ
  → printResponse разбирает OK STRING и выводит результат
```

## Сервер и сокеты

1. `socket(AF_INET, SOCK_STREAM, 0)` создаёт TCP-сокет IPv4.
2. `sockaddr_in` заполняется локальным адресом INADDR_ANY и портом 12345.
3. `bind` привязывает сокет к этому адресу. Простое заполнение структуры ещё не меняет сокет.
4. `listen` разрешает принимать подключения.
5. `accept` ждёт подключение и возвращает отдельный сокет для общения с клиентом. Слушающий сокет продолжает существовать.
6. Внутренний цикл читает запрос, выполняет команду, отправляет ответ.
7. После /quit или отключения сокет сессии закрывается, сервер снова вызывает accept.

`listen(..., 3)` задаёт параметр очереди ожидающих подключений, а не предел количества клиентов за всё время работы. Сервер последовательно обрабатывает одну сессию; другие подключения могут ждать.

## Где находится состояние

Сразу после accept, перед циклом команд:

```cpp
std::mt19937 generator(5489u);
std::vector<std::string> history;
bool quit = false;
```

`generator` хранит состояние генератора псевдослучайных чисел. `history` — последовательность строк. Переменные создаются на новое соединение, поэтому разные сессии не разделяют историю и состояние генератора.

В handleCommand передаются ссылки `&`: изменения затрагивают эти же объекты из main. Если создать генератор внутри handleCommand, он будет сбрасываться на каждой команде — это нарушит последовательность.

## Seed и генерация

Seed задаёт начальное состояние генератора. Пример последовательности действий:

```text
/seed 42
/generate DIGITS 10
/seed 42
/generate DIGITS 10
```

Две строки /generate будут одинаковыми при выполнении в той же реализации программы. Генератор детерминированный: одинаковое начальное состояние и одинаковая последовательность операций дают одинаковый результат.

Одна и та же строка не обязана совпадать в разных стандартных библиотеках C++: преобразование чисел в диапазон через uniform_int_distribution может различаться. Клиент Windows может общаться с сервером macOS и наоборот — это не мешает протоколу.

`alphabetForType` возвращает строку со всеми допустимыми символами. Например, DIGITS возвращает `0123456789`.

```cpp
std::uniform_int_distribution<int> pick(0, static_cast<int>(alphabet.size()) - 1);
value += alphabet[static_cast<std::size_t>(pick(generator))];
```

`pick(generator)` выбирает индекс от 0 до последнего индекса включительно. По этому индексу берётся символ. Цикл повторяется заданное число раз.

В литерале алфавита PUNCT `\` записывает одну обратную косую черту, а `"` — одну кавычку. На уровне сетевого протокола экранирования нет: эти символы передаются как есть.

## Команды в handleCommand

- /seed: проверить число, вызвать `generator.seed(...)`, вернуть OK SEED. Историю не очищать.
- /generate: проверить тип и длину, получить случайные символы, добавить результат в историю, вернуть OK STRING.
- /check: проверить тип и длину строки, найти каждый символ в алфавите. Если символ не найден (`std::string::npos`), вернуть OK CHECK NO. Иначе YES. Генератор не вызывается.
- /history: собрать строку OK HISTORY, число элементов и сами значения через пробел.
- /quit: установить quit в true и вернуть OK BYE. Main сначала отправит ответ, затем выйдет из внутреннего цикла.

/check даёт эвристику по составу символов. Строка 12345 подходит DIGITS, даже если человек набрал её вручную. ALNUM допускает строку только из букв или только из цифр, поскольку каждый её символ входит в общий алфавит.

## Последние пять результатов

```cpp
history.push_back(value);
if (history.size() > 5) history.erase(history.begin());
```

Добавляем результат в конец. Если результатов стало шесть, удаляем первый, самый старый. /history показывает оставшиеся от старого к новому. Повторяющиеся результаты тоже учитываются как отдельные генерации.

Длина результата ограничена 128 символами. Самый длинный ответ истории: 12 байт префикса `OK HISTORY 5` плюс 5 × (пробел + 128 байт) = 657 байт без LF. Это меньше лимита 1024.

## Проверка ввода

`std::istringstream` читает токены строки через `>>`. Отсутствующий или лишний токен — BAD_FORMAT. Например, /generate DIGITS и /history 1 имеют неправильное число аргументов.

`parseUnsigned` сначала убеждается, что строка содержит только цифры. Поэтому -1, +1, 1.5, 1e3 и 12abc отвергаются. Затем поток читает unsigned long long и обнаруживает слишком большое число. Для длины и seed отдельно проверяется допустимый диапазон.

Сначала идут все проверки, затем изменения генератора/истории. Ошибочный запрос состояние не меняет. Ошибки команд возвращают ERR, после чего сессию можно продолжать. Слишком длинное или оборванное сообщение завершает сессию.

## Почему сообщения заканчиваются LF

TCP передаёт поток байтов: один send не обязан соответствовать одному recv. Запрос может прийти частями, несколько запросов — подряд в одном потоке.

`receiveLine` читает по одному байту и останавливается на LF. Начало следующей команды остаётся в буфере ОС. CR перед LF удаляется, поэтому понимается и CRLF. Чтение по одному байту удобно для объяснения; для больших потоков обычно читают блоками.

Результаты receiveLine: LINE_OK — строка готова; CLOSED — другая сторона закончила передачу; IO_ERROR — сетевая ошибка; TOO_LONG — больше 1024 байт; INCOMPLETE — передача закончилась до LF посреди строки.

`sendLine` добавляет LF. `send` может принять только часть данных, поэтому цикл досылает оставшуюся часть. Успех send означает приём байтов локальной ОС; выполнение команды подтверждает ответ приложения OK.

## Клиент

Клиент создаёт сокет, заполняет адрес сервера, вызывает connect. Если bind не вызывался, локальный адрес и порт назначает ОС. По умолчанию сервер — 127.0.0.1:12345; другой IPv4-адрес задаётся аргументом запуска.

После connect клиент читает строку из консоли, отправляет её и ждёт ответ. `printResponse` разбирает OK STRING, OK SEED, OK CHECK, OK HISTORY и ERR. Для истории проверяется количество значений. OK BYE обрабатывается в main и завершает цикл. Конец консольного ввода тоже отправляет /quit.

## Windows и macOS

| Windows | macOS |
| --- | --- |
| WSAStartup перед работой с сокетами | Отдельная инициализация не нужна |
| SOCKET | int |
| INVALID_SOCKET | -1 |
| closesocket | close |
| shutdown(..., SD_SEND) | shutdown(..., SHUT_WR) |
| WSACleanup после закрытия сокетов | Не требуется |
| ws2_32 при линковке | Сокеты доступны из системной библиотеки |

На macOS SIGPIPE игнорируется, чтобы запись в разорванное соединение возвращала ошибку send. SO_REUSEADDR облегчает повторный запуск сервера на прежнем порту. EINTR означает, что системный вызов прерван сигналом; код повторяет его.
